# 校园信息整合网站项目说明书

版本：v0.1  
用途：供项目组成员及其 AI 助手理解当前项目目标、功能边界与后续开发方向  
项目性质：本科《人类工效学》课程大作业

---

# 1. 项目背景

我们希望解决校园信息过于分散、学生查找信息成本较高的问题。

目前的核心思路不是做一个“大而全”的校园门户，而是把几类高频、分散、难找的信息重新组织成更符合学生实际使用习惯的形式。

当前计划把网站做成一个统一入口，其中优先实现两个主要模块：

1. **校园办事指南**
2. **浙大美食点评墙**

第三个模块“校园信息源导航”暂缓，后续有时间再加入。

---

# 2. 项目总体目标

整个网站的目标是：

> 让学生更快地找到自己真正需要的校园信息，并减少在多个平台、公众号、系统之间反复查找的成本。

当前重点不是做复杂功能，而是完成一个：

- 可以实际打开和使用；
- 可以搜索；
- 可以继续补充数据；
- 可以让不同用户共同使用；
- 后续能够用于人因工程课程中的用户测试和效果验证；

的初步 Demo。

---

# 3. 网站整体结构

整个项目集成在一个网页中。

首页主要负责把用户引导到不同功能模块。

建议首页包含：

- 项目名称；
- 一句话说明；
- 两个主要模块入口；
- 第三个模块可以暂时显示“后续上线”。

建议结构：

```text
首页

├── 校园办事指南
│   ├── 搜索问题
│   ├── 查看搜索结果
│   └── 查看具体解决方案
│
├── 浙大美食点评墙
│   ├── 搜索菜品
│   ├── 浏览菜品卡片
│   ├── 查看菜品详情
│   ├── 创建新卡片
│   └── 对菜品进行 1～5 星评分
│
└── 校园信息源导航
    └── 暂缓开发
```

# 4. 模块一：校园办事指南

## 4.1 模块目标

解决学生在处理校园事务时：

- 不知道去哪里办；
- 不知道需要什么材料；
- 不知道开放时间；
- 不知道应该进入哪个系统；
- 相关信息分散在多个网站、公众号或推文中；

的问题。

核心思路：

> 用户不需要先知道“应该进入哪个系统”，只需要直接搜索自己遇到的问题。

---

## 4.2 使用方式

用户进入“校园办事指南”后，可以看到一个明显的搜索框。

示例提示：

```text
你遇到了什么问题？

例如：
校园卡丢了
怎么预约场地
校医院怎么挂号
```

用户输入关键词后，网站从已经收集好的问题中进行匹配。

例如搜索：

```text
校园卡
```

可能显示：

```text
校园卡丢了怎么办？
校园卡在哪里补办？
校园卡怎么挂失？
```

用户点击对应问题后，进入具体答案页。

---

## 4.3 问题详情页

每一个问题的答案尽量按照统一结构整理。

建议包含：

```text
问题：
校园卡丢了怎么办？

一句话说明：
……

办理步骤：
1.
2.
3.

需要准备：
……

办理地点：
……

开放时间：
……

联系方式：
……

参考指南：
官方网页 / 官方推文 / 其他可靠来源

信息来源：
……

最后核验时间：
……
```

---

## 4.4 信息收集方式

组员在收集资料时，不要只发一堆链接。

统一按照：

> **问题 + solution**

的形式整理。

建议模板：

```text
问题：

关键词：

一句话答案：

具体步骤：

需要材料：

办理地点：

开放时间：

联系方式：

参考推文 / 网页：

原始来源：

核验日期：

备注：
```

---

## 4.5 搜索功能

搜索功能可以现在先搭好框架，等收集到真实资料后再补充内容。

第一阶段只需要做“站内搜索”，不需要互联网搜索，也不需要 AI 搜索。

至少应该能够根据：

- 问题标题；
- 关键词；
- 简短描述；

进行匹配。

例如：

```text
搜索“校园卡”
→ 匹配所有和校园卡相关的问题
```

# 5. 模块二：浙大美食点评墙

## 5.1 模块目标

解决学生在校园内外找吃的时：

- 不知道某个菜好不好吃；
- 不知道价格大概多少；
- 不知道在哪里；
- 想找其他同学的真实评价；
- 同一个菜的信息零散在群聊、小红书、朋友圈等地方；

的问题。

这一模块希望做成一个简单版的“校园大众点评”。

---

## 5.2 整体结构

美食墙分成两个主要部分：

### 校内食堂

主要围绕：

```text
食堂
→ 菜品
```

展开。

例如：

```text
某食堂
├── 石锅拌饭
├── 炒饭
├── 面
└── 其他菜品
```

### 校外美食

主要用卡片形式展示。

例如：

```text
草莓蛋糕
某某面包店
¥18
⭐ 4.5
```

---

# 6. 美食搜索功能

美食墙必须提供站内搜索。

用户可以搜索：

- 菜名；
- 食堂；
- 店铺；

例如：

```text
搜索“石锅”
→ 找到“石锅拌饭”

搜索“玉湖”
→ 找到玉湖相关的菜品
```

搜索结果以卡片形式展示。

---

# 7. 美食卡片

每一张菜品卡片建议包含：

## 必填

- 菜品名称
- 地点 / 食堂 / 店铺
- 校内或校外
- 1～5 星评分

## 可选

- 价格
- 图片
- 一句话评价
- 简单标签

例如：

```text
石锅拌饭

地点：某食堂
价格：¥15
评分：⭐ 4.3
评分人数：21 人

图片

一句话评价：
分量大，价格合适。
```

---

# 8. 用户创建美食卡片

用户可以主动创建一个新的美食卡片。

建议流程：

```text
点击“发布美食”

↓

填写菜品名称

↓

填写地点 / 食堂 / 店铺

↓

选择：
校内 / 校外

↓

填写价格（可选）

↓

上传 1 张图片（可选）

↓

给出自己的 1～5 星评分

↓

写一句评价（可选）

↓

点击发布
```

发布成功后：

> 这张卡片应该能够被其他用户搜索到。

---

# 9. 用户评分功能

其他用户进入某个菜品卡片后，可以看到：

```text
当前平均评分：
⭐ 4.2

17 人评分
```

用户可以选择：

```text
☆ ☆ ☆ ☆ ☆
```

并提交 1～5 星评分。

提交后：

- 评分人数增加；
- 平均评分重新计算；
- 其他用户也能够看到新的评分结果。

---

# 10. 多人共享这一点非常重要

我们希望实现的是：

```text
用户 A 创建一张美食卡片

↓

用户 B 在自己的电脑 / 手机上搜索到

↓

用户 B 给它评分

↓

用户 C 也能看到更新后的评分
```

因此这部分最终不能只把数据保存在某一台电脑上。

后续需要使用一个共享的在线数据库。

目前可以考虑：

> Supabase

可以把它简单理解为：

- 在线数据库；
- 图片存储空间；
- 网站的数据后端。

目前不要求负责开发的组员自己理解数据库原理，可以借助 GPT / Codex 完成。

# 11. 关于登录

当前版本暂时不要求：

- 注册账号；
- 登录；
- 用户主页；
- 社交关系。

第一版以“匿名使用”为主。

目标优先级是：

> 先把“创建卡片 → 搜索 → 查看 → 评分”这一条完整流程跑通。

是否需要登录，可以后续再讨论。

---

# 12. 关于重复菜品

如果一个菜已经有人创建过，另一个用户又想新建相同菜品，可能出现重复卡片。

第一版可以采用简单处理方式：

当用户输入菜名准备发布时，网站先提示：

```text
可能已有类似菜品：

石锅拌饭 · 某食堂
⭐ 4.3

[查看已有卡片]

[仍然创建新卡片]
```

暂时不需要复杂的自动去重算法。

# 13. 模块三：校园信息源导航

这一部分目前先不急着开发。

- 学术讲座
- 竞赛

- 实习就业
- 体育
- 生活服务

进行分类。

当前可以在首页保留入口，但显示：

```text
校园信息源导航
后续上线
```

# 17. 项目最终交接

网站完成后，需要能够转移到组长电脑继续使用。

最简单的交接方式：

> 把完整工程文件夹打包成 ZIP 发给组长。

工程中应该保留：

- 源代码；
- 页面文件；
- 配置文件；
- package.json；
- README；
- 数据文件；
- 其他运行所需文件。

不需要把 `node_modules` 整个一起打包。

# 18. 如果使用 Supabase

如果后续接入 Supabase，推荐：

> Supabase 项目由组长账号创建。

开发同学在自己的电脑上连接这个项目并继续开发。

这样：

- 开发同学只负责写网页；
- 最后只需要把工程 ZIP 发给组长。

可以避免出现：

> 代码已经转移，但数据库还在开发同学账号里。

# 20. 项目的人因工程意义

这个项目最终不是单纯“做一个网站”。

后续课程展示需要验证：

> 信息整合后，学生是否真的更容易找到目标信息。

例如可以设计实验比较：

```text
原有方式
vs
使用本网站
```

比较：

- 完成任务时间；
- 搜索次数；
- 是否成功；
- 主观难度；
- 信息获取满意度。

因此在开发过程中应优先保证：

- 搜索入口明显；
- 页面结构清楚；
- 重要信息容易找到；
- 操作反馈明确；
- 不增加不必要的操作步骤。

# 24. 首页设计

## 24.1 首页目标

首页只承担两个任务：

1. 让用户在 5 秒内理解网站是做什么的；
2. 让用户快速进入“校园办事”或“美食点评”。

不要把首页做成信息流。

---

## 24.2 首页首屏

首屏建议结构：

```text
标题：
浙大校园信息，一处找到

副标题：
更快找到校园办事指南和真实美食评价，
减少在多个平台之间反复查找。

[校园办事指南]
遇到问题，直接搜索怎么解决

[浙大美食点评]
搜索菜品、查看评价、发布自己的美食卡片
```

两个模块入口应做成两张明显的大卡片。

---

## 24.3 首页视觉重点

优先级：

```text
网站定位
↓
两个主要入口
↓
简短说明
↓
其他内容
```

不要把大量介绍文字放在首屏。

# 25. 校园办事页

```text
我有一个问题
↓
输入关键词
↓
找到对应问题
↓
打开解决方案
```

## 25.2 页面布局

建议：

```text
页面标题：
校园办事指南

不用先知道该进哪个系统，直接搜索你遇到的问题。

热门 / 常见问题

[校医院怎么挂号？]

```

---

## 25.3 搜索框

搜索框必须是页面最明显元素之一。

占据较大宽度。

placeholder 示例：

```text
搜索你的问题，例如：校园卡丢了、预约场地……
```

用户输入后：

- 实时显示匹配结果，或；
- 点击搜索按钮后显示结果。

二者选一种即可。

V1 更推荐：

> 输入即筛选

因为实现简单，反馈直接。

## 25.4 搜索结果卡片

一条搜索结果建议显示：

```text

先挂失，再前往指定地点办理……

[查看解决方案]
```

不要直接在列表页塞完整答案。

# 27. 办事搜索的技术行为

V1 搜索不需要 AI。

对以下字段做关键词匹配：

```text
问题标题
关键词
```

# 57. 匿名浏览与浙大邮箱登录

2026-10-13按用户新要求更新：浏览不要求邮箱登录；发布、编辑、可恢复删除和恢复要求已验证的@zju.edu.cn邮箱。提供首次匿名身份绑定及已有邮箱账号登录，不收取邮箱密码。真实发信服务未配置时入口明确暂未开放。以下匿名机制继续用于浏览及既有评分身份。

推荐使用：

> **Supabase Anonymous Auth（匿名认证）**

网站第一次打开时，为当前用户创建一个匿名 Supabase 用户身份。

后续评分时使用该用户的 `user_id` 作为身份标识。

优点：

- 不需要用户注册；
- 不需要密码；
- 适合课程 Demo；
- 可以在数据库中识别“同一个匿名用户”；
- 可以配合数据库约束限制重复评分。

注意：

> 这种方式只能较可靠地识别“同一浏览器 / 同一匿名会话中的用户”。

如果用户：

- 清除浏览器数据；
- 更换浏览器；
- 更换设备；

可能会获得新的匿名身份。

因此它适合课程原型，但不能视为正式产品级身份认证。

如果未来需要真正限制“每个现实中的人只能评分一次”，则需要手机号、邮箱或学校统一身份认证。

# 58. 一人不可重复评分的实现规则

V1 规则：

> 同一个匿名用户，对同一个菜品只能存在一条评分记录。

推荐数据库中建立评分表：

```text
ratings

id
food_id
user_id
rating
created_at
```

并设置唯一约束：

```text
(food_id, user_id) UNIQUE
```

这样即使前端逻辑出现问题，数据库也能阻止同一匿名用户对同一道菜重复新增评分。

V1 默认行为：

- 如果用户尚未评分：允许提交；
- 如果用户已经评分：显示“你已经评分过该菜品”；
- V1 暂不支持修改评分。

如果未来需要修改评分，可再增加“更新已有评分”的功能。

# 62. 作者编辑、删除与恢复

2026-10-13用户批准替换此前“发布后不可删除”的限制：

- 已验证浙大邮箱的作者可以编辑自己的菜品信息、删除及恢复自己的发布；提供“我的发布”入口。
- 删除须确认，采用可恢复撤下；公共列表和详情隐藏，评分保留，恢复后重新计入原统计。公开图片不在本轮物理清除。
- 编辑不改变创建者或评分。替换图片用本人目录的新文件，不覆盖原对象；保存失败保留填写。
- 服务端检查真实身份、归属及更新时间；他人、未验证账号及旧版本不能越权或覆盖。
- 在原匿名会话中绑定邮箱保留同一用户ID；另一已注册账号与旧匿名身份不自动合并。
- 评分仍保持本轮原有一次提交且不可修改/删除规则；管理员清理与永久删除另行设计。

不要求用户点击“搜索”按钮后才能看到结果。

# 64. 搜索行为细节

建议加入约 200～300ms 的 debounce。

即：

> 用户停止输入约 0.2～0.3 秒后再执行搜索。

这样可以避免每输入一个字符都立刻向 Supabase 发起请求。

这属于技术优化，由 AI 自动实现即可，组员无需理解具体代码。

---

# 65. 网络与加载失败

V1 不做复杂离线能力。

规则很简单：

> 没有网络或 Supabase 请求失败，就显示失败提示。

例如：

```text
加载失败，请检查网络后重试。
```

或者：

```text
暂时无法获取数据，请稍后再试。
```

不要求：

- 离线缓存；
- 自动同步；
- 多次后台重试；
- Service Worker；
- PWA 离线模式。

---

# 66. 加载状态

虽然失败处理保持简单，但页面必须避免“突然空白”。

建议：

加载时：

```text
正在加载……
```

加载成功：

显示内容。

加载失败：

```text
加载失败，请重试。
```

# 69. Supabase 权限原则

由于使用匿名认证，开发 AI 需要正确配置 Supabase RLS（Row Level Security）。

V1 目标：

### foods

公开访问者可读取未删除菜品。已验证浙大邮箱用户通过事务发布并记录首次评分；作者通过受限接口编辑、删除及恢复自己的发布。普通客户端不能直接修改作者或评分。新旧版本过渡的require_email开关须在正式开通时开启，不把前端检查当权限保护。

### ratings

匿名用户：

- 可以读取；
- 可以新增自己的评分；
- 同一个用户对同一个 food 只能有一条评分；
- V1 不提供修改；
- 不提供删除。

具体策略由开发 AI 根据 Supabase 当前推荐方式配置。
