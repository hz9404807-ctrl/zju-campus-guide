## 组长操作

1. 等同学结束本轮测试，打开原 Supabase 项目 → SQL Editor，新建一次查询。
2. 粘贴 [`withdraw-acceptance-foods.sql`](../supabase/maintenance/withdraw-acceptance-foods.sql) 全文，保留末尾 `rollback;`，运行预览。应只出现上表 4 条、保留评分数分别 3/1/1/2；该次预览会整体回滚。
3. 核对无误后，只把最后一行改为 `commit;`，再次运行。这是一次可恢复的**撤下**：列表与公开详情不再展示它们，原作者仍可在自己的发布中管理，评分历史显示条目当前不可用。与永久删除存在区别。
4. 刷新美食列表，核对四条消失、真实菜品仍在；用原作者账号确认四条为已撤下。无需重新部署网站或重新执行初始化迁移。

操作要求项目数据库所有者权限。普通浙大邮箱登录和前端 publishable key 没有跨作者清理权限；无需向 AI 提供管理密钥或管理会话。脚本按精确 ID、名称、地点、价格、图片路径、说明、标签、时间、评分计数及均分验证；不匹配或锁等待超时会整体中止，不按“测试”关键词模糊删除。

撤下会把操作前记录保存在私有 `campus_private.acceptance_food_cleanup`，RLS 开启且普通客户端及 service_role 的表权限显式撤回；该表不进入前端接口。脚本不会删除 `ratings`、Storage 对象或 `auth.users`。原图片的公开 Storage URL 仍可能可访问，因此不能把本次撤下称为永久删除或图片删除。

## 回退

在同一 SQL Editor 粘贴 [`restore-acceptance-foods.sql`](../supabase/maintenance/restore-acceptance-foods.sql)，先按默认 `rollback;` 查看四条恢复预览，再将末尾改为 `commit;` 执行。恢复使用私有备份，只允许四条记录仍处于本次撤下状态、且没有新编辑时整体恢复；有后续变化会中止。保留私有审计表，不覆盖新的更新时间、不删除审计记录。重复清理会中止，避免二次覆盖备份。

如后续确需永久删除，需另外核对图片和评分处理范围后操作；本轮交付的是可恢复撤下方案。

## 本地验证

`npm test` 中的 `food-fixture-maintenance.test.mjs` 使用隔离 PGlite 数据库执行原 SQL，覆盖默认回滚、精准四条撤下、评分保留、恢复、重复执行和数据已变化时中止。测试数据只存在本机临时数据库；它不代表云端维护已经执行。
